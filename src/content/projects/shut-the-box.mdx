## Table of Contents

## My History With Shut the Box
As a kid, I was gifted a physical version of Shut the Box for Christmas one year,
and I found it to be surprisingly entertaining given how simple the game first seemed.
Still, the act of rolling the dice and the suspense of seeing what they'd turn up was
exciting, and the strategy of choosing what combination of tiles to flip turned out to
be more complex than it first appeared.

Thinking on it now, I believe that there are 3 primary components that make Shut the Box fun.
1. **The physical, haptic interaction** – Rolling the dice, flipping the wooden tiles, and,
for the particularly lucky, shutting the titular box. Physically speaking, the design 
of this game is deceptively genius. The box in which it's played is not only iconic, 
but also convenient and satisfying. It makes the game easily portable, provides a 
perfect space in which to roll the dice, and gives the player something to shut.
Beautiful.
2. **The strategy** – As a kid playing Shut the Box for the first time, I had never heard
of Bayesian statistics before, but still, Shut the Box was a fair introduction to some
of the basic concepts. It's interesting that even children begin to develop their own
set of axioms when playing games like this. For example, never flip down multiple tiles
when you could instead flip a tile that is their sum. Coming up with strategies, putting
them into practice, seeing the results, and then refining those strategies is half the fun.
3. **The uncertainty** – No matter how perfect your strategy, victory is never guaranteed.
If it were, then the game would get pretty boring pretty quickly. You know what I call a
game that can be solved once and then have that solution always work? A puzzle. 
Now, those are fun, too, but they're generally much less replayable.

Years later, I felt a hankering to play Shut the Box again, but to my dismay, there
weren't any virtual versions of it available on the web (at least, none that I found
sufficient). Thus, seeing it as a good opportunity to stretch my JavaScript skills as 
well as my algorithm skills, I set about making my own implementation of Shut the Box.

## Game Logic
The part of this project that I enjoyed the most was coming up with the logic used to change the state of the tiles in response to the target value of the dice, and the remaining unused tiles. This algorithm is responsible for detecting when the player's encountered a game over, as well as disabling unused tiles that can no longer be used in a valid combination based on the tiles the player has already selected. [Here's the algorithm in the code](https://github.com/cbmitchell/Shut-the-Box/blob/22bdd5e2ed6f06fbcf8ea4b154c3159e583d1eb0/index.html#L255-L283):
```javascript
const checkSolutions = function() {
  unusedNums = [];
    for (i = n-1; i >= 0; i--) {
      if (!usedNums[i] && !selectedNums[i]) {
        unusedNums.push(i+1);
      }
    }
    solutions = checkSolutionsHelper(unusedNums, sum - tempSum, 0);
    return solutions;
};

// k = new sum for recursive call
// i = pointer for where to start iterating in this recursive call
const checkSolutionsHelper = function(arr, k, i) {
  let solutions = [];
  for (let j = i; k <= tri(arr[j]); j++) {
    let subSolutions = [];
    if (arr[j] == k) {
      subSolutions.push([]);
    }
    if (arr[j] < k) {
      subSolutions = checkSolutionsHelper(arr, k - arr[j], j+1);
    }
    for (let s = 0; s < subSolutions.length; s++) {
      solutions.push([arr[j]].concat(subSolutions[s]));
    }
  }
  return solutions;
};
```
The function uses state variables which is why it doesn't have any arguments. Here's what each state variable in there represents:
- `n` – number of tiles (used and unused)
- `usedNums` – A boolean array of length `n`. The indexes of the array correspond to the tile with the same value as the index. If the boolean at that index is `true`, the tile is "used" and therefore unavailable.
- `selectedNums` – Similar to `usedNums`, except the boolean values represent whether a given tile has been selected. A tile is "selected" after the player selects it but before the player ends their turn. If the player ends their turn while a tile is selected, then it becomes used.
- `sum` – The target sum that was rolled on the dice for that turn
- `tempSum` – The sum of all the currently selected tiles
- `tri(n)` – A small util function that calculates the value of the *n*th [triangular number](https://en.wikipedia.org/wiki/Triangular_number)

The `solutions` array returned by `checkSolutionsHelper` (and `checkSolutions`) is a 2D array.
- It contains one array for each possible combination of available tiles that could be summed to equal the target sum.
- Solution arrays are arrays of integers, with each integer corresponding to an available tile.
### Annotated Solution-Finding Algorithm
```js
const checkSolutions = function() {
  // Initialize empty array of unused tiles
  unusedNums = [];

  // Loop through the value of every tile in descending order.
  // This is done to populate the unusedNums array with the values
  //   of tiles that are still available for selection
  //   (i.e. neither used nor already selected)
  for (i = n-1; i >= 0; i--) {
    if (!usedNums[i] && !selectedNums[i]) {
      unusedNums.push(i+1);
    }
  }

  // First invocation of the recursive function
  // Call it with all unused tiles (in descending order), 
  //   the remaining target sum, and 0 index
  // Note that the unusedNums array is never mutated in the 
  //   recursive fns. It's always passed with the exact same value,
  //   but the index we pass as the third parameter effectively 
  //   lets us use subsets of it.
  solutions = checkSolutionsHelper(unusedNums, sum - tempSum, 0);

  // After the recursive function exits, return the result.
  return solutions;
};
  
// k = new sum for recursive call
// i = pointer for where to start iterating in this recursive call
const checkSolutionsHelper = function(arr, k, i) {
  let solutions = [];
  // Here, the restriction of k <= tri(arr[j]) is an optimization.
  // This function would work without it, but would end up doing 
  //   some unnecessary calculation.
  // Basically, we're looking at smaller and smaller subsets of the 
  //   array of available tiles which is sorted in descending order.
  // The check for this loop prevents us from running calculations
  //   on subarrays that are too small to possibly sum up to the
  //   target sum, k.
  // So, for example, say that the available tiles are [4, 3, 2, 1].
  // This means arr == [4, 3, 2, 1].
  // We would look at [4, 3, 2, 1], then [3, 2, 1], [2, 1], & [1].
  // Now, say we have a target sum of 8 (i.e. k == 8).
  // In our first iteration, j == 0.
  // tri(arr[j]) –> tri(arr[0]) –> tri(4) –> 10
  // 10 <= 8, so we'd run the logic inside the loop.
  // On our second iteration, j == 1.
  // tri(arr[j]) –> tri(arr[1]) –> tri(3) –> 6
  // 6 <= 8, so we'd stop the loop and return the solutions.
  for (let j = i; k <= tri(arr[j]); j++) {
    let subSolutions = [];

    // This is our BASE CASE for the recursive function.
    // If the tile for this iteration is equal to the target sum,
    //   then it's a solution on its own.
    // Adding an empty array to subSolutions here will ensure that
    //   this invocation of the function will ultimately return a 2D
    //   array that looks like [[arr[i]]]
    // It's kindof a cheeky implementation.
    // I might want to refactor this to be a little clearer.
    if (arr[j] == k) {
      subSolutions.push([]);
    }

    // If the current tile is small enough to be included in a
    //   solution, call this function recursively on the target sum
    //   minus this tile's value.
    // The recursive call will return an array of subsolutions, 
    //   which we'll concatenate with the current tile in order to
    //   produce solutions.
    if (arr[j] < k) {
      subSolutions = checkSolutionsHelper(arr, k - arr[j], j+1);
    }
    
    // For each subsolution returned by the recursive call
    //   (or the empty one from when the current tile is equal to
    //   the target sum), attach the current tile to the front of
    //   it and return it as a potential solution.
    for (let s = 0; s < subSolutions.length; s++) {
      solutions.push([arr[j]].concat(subSolutions[s]));
    }
  }
  return solutions;
};
```
## Potential Enhancements
I might still go back to this project and make further enhancements to it.
- I'd like to see if I can further optimize the algorithm for dynamically 
calculating which tiles are viable.
    - It can certainly be improved via memoization, especially for particularly large numbers of tiles.
- Do a little tidying of the general look of it.
- Add statistics
    - Show the player what their odds of a game over are on the next roll based 
    on the tiles they've selected.
- Introduce some settings that users can use to customize their experience.
    - Dark mode
    - Number of dice (not just set automatically)
    - Showing the actual roll value on game over
    - [Alternate gameplay modes](https://en.wikipedia.org/wiki/Shut_the_box#Variants)
    - Alternate scoring systems
